## 1. 值得留的算法

### 1.1 `TileRunner` —— 万能矿脉/洞穴生成器

**来源**：`Terraria-Source-Code-master`，`WorldGen.cs:37296`

一个函数同时干三件事：铺矿脉、挖洞穴、生成地形块。**这是本次盘点里性价比最高的一个。**

原理：一个点带着速度向量往前跑，每步在它周围按曼哈顿距离填一个圆，圆的半径随剩余步数衰减：

```
radius = strength * (steps / initial_steps)          # 越到后面越细，矿脉自然收尾
每步填充：|k - pos.x| + |l - pos.y| < strength * 0.5 * (1 + rand(-10,11) * 0.015)
每步末：pos += velocity
        velocity += rand(-10,11) * 0.05              # 抖动，走出来的才是曲线不是直线
type < 0  → 挖空（洞穴）
type == -2 → 挖空并灌水
type >= 0 → 填该种方块
```

**为什么好**：矿脉现在是用噪声阈值切的，出来的是一片均匀的斑点；`TileRunner` 出来的是**有走向、有粗细变化、末端收尖**的脉状物，一眼就像矿。

**落到 ColonySim**（`terrain.gd` 的生成阶段）：

```gdscript
## 一条矿脉/洞穴：从 (x,y) 出发跑 steps 步，边走边填半径 strength 的圆。
## 半径随剩余步数衰减，所以脉是两头细中间粗的。carve=true 时是挖洞而不是填矿。
static func tile_runner(tiles: PackedByteArray, x: int, y: int, strength: float,
        steps: int, kind: int, carve := false, rng: RandomNumberGenerator = null) -> void:
    if rng == null:
        rng = RandomNumberGenerator.new()
    var px := float(x)
    var py := float(y)
    var vx := rng.randf_range(-1.0, 1.0)
    var vy := rng.randf_range(-1.0, 1.0)
    var total := steps
    while steps > 0:
        var r := strength * (float(steps) / float(total))
        var ri := int(ceil(r))
        for dy in range(-ri, ri + 1):
            for dx in range(-ri, ri + 1):
                # 曼哈顿距离 + 抖动：每格边界都毛毛的，不是标准圆
                var jitter := 1.0 + rng.randf_range(-0.15, 0.15)
                if absf(float(dx)) + absf(float(dy)) < r * 0.5 * jitter:
                    var tx := int(px) + dx
                    var ty := int(py) + dy
                    if tx < 0 or ty < 0 or tx >= W or ty >= H:
                        continue
                    if carve:
                        tiles[idx(tx, ty)] = Kind.CAVE
                    else:
                        tiles[idx(tx, ty)] = kind
        px += vx
        py += vy
        vx += rng.randf_range(-0.5, 0.5)
        vy += rng.randf_range(-0.5, 0.5)
        steps -= 1
```

调用示例（替换现在的「噪声切矿脉」那一步）：

```gdscript
for i in 3 + _rng.randi() % 4:
    var vein := rock_tiles.pick_random()          # 从石山里随机挑一个起点
    tile_runner(tiles, vein.x, vein.y, 4.0, 40, Kind.IRON, false, _rng)
```

**工作量**：半天。改动局限在 `terrain.gd` 的生成函数里，不动渲染、不动寻路。

### 1.2 光照：BFS 洪泛 vs 方向扫描

两个来源给了两种做法，都记下来。

**做法 A —— BFS 洪泛（`TerrariaClone-main`，`TerrariaClone.java:5187 resolveLightMatrix`）**

```java
取出队首格 (x,y)，按光源强度点亮它
  for 四个方向:
    if 目标格不透明:  if (lights[目标] <= lights[当前] - 1.0) { lights[目标] = lights[当前] - 1.0; 入队 }
    else:            if (lights[目标] <= lights[当前] - 2.0) { lights[目标] = lights[当前] - 2.0; 入队 }
```

**关键点**：空气衰减 1、实体衰减 2，且**只在变亮时才继续传播**（`<=` 判断），队列自然收敛，不会死循环。一个队列同时处理所有光源，天然叠加。

**做法 B —— 四向扫描（`Terraria-Source-Code-master`，`Lighting.cs:3150 LightColor`）**

不做 BFS，而是**沿行、沿列各扫两遍**（下→上、右→左），每次都用一个「游标亮度」沿路乘衰减：

```
negLight  = 0.9    # 穿过一格空气
negLight2 = 0.54   # 穿过一格实体  ← 穿墙衰减快得多
```

扫四遍就收敛成平滑梯度，而且可以**分摊到多帧**（一帧扫一个方向），大世界也不卡。

| | BFS 洪泛 | 四向扫描 |
|---|---|---|
| 精度 | 准（真最短衰减路径） | 近似（斜向会偏亮） |
| 改动一格时 | 只重算受影响区域，**增量更新** | 得重扫 |
| 实现难度 | 低 | 低 |
| 适合 | **本项目**（挖墙/建墙会实时改地图） | 静态大世界 |

**落到 ColonySim**：现在的 `night_overlay.gd` 是在整屏遮罩上画半透明柔光圆，光**会穿墙**——把火把插在房子外面，屋里也亮。换成做法 A，光只走能通行的格子，营火的光会绕着墙拐弯，房间内外的明暗立刻有说服力。

`night_overlay.gd` 里加一张 `float` 亮度图（128×128），入夜时算一次，之后只在建筑增减时增量重算：

```gdscript
## 光照洪泛：从所有光源出发，空气每格 -1、实体每格 -2，只在变亮时继续传。
## 返回 PackedFloat32Array（长度 W*H），值 0~1。
## 用 BFS 而不是逐帧扫描：挖墙建墙会实时改地图，增量重算比全图重扫便宜。
static func flood_light(sources: Array, opaque: PackedByteArray) -> PackedFloat32Array:
    var light := PackedFloat32Array()
    light.resize(W * H)
    var queue: Array[Vector2i] = []
    for s in sources:                       # s = {"tile": Vector2i, "power": float}
        var i := idx(s["tile"].x, s["tile"].y)
        if light[i] < s["power"]:
            light[i] = s["power"]
            queue.append(s["tile"])
    var head := 0
    while head < queue.size():              # 用下标当队首，别用 pop_front（O(n)）
        var cur: Vector2i = queue[head]
        head += 1
        var cur_l := light[idx(cur.x, cur.y)]
        for d in [Vector2i.UP, Vector2i.DOWN, Vector2i.LEFT, Vector2i.RIGHT]:
            var n := cur + d
            if n.x < 0 or n.y < 0 or n.x >= W or n.y >= H:
                continue
            var ni := idx(n.x, n.y)
            var cost := 2.0 if opaque[ni] == 1 else 1.0
            if light[ni] <= cur_l - cost:   # 只在变亮时入队 —— 收敛靠这一行
                light[ni] = cur_l - cost
                queue.append(n)
    return light
```

> 顺带一个 GDScript 性能点：`Array.pop_front()` 是 O(n)，队列大了会拖垮。用 `head` 下标往前走，别真的删元素。

**工作量**：一天（含渲染改法）。这是六个来源里**画面收益最大**的一项。

### 1.3 RimWorld 的三层工作模型 —— 直接影响 AI 提示词设计

**来源**：`game/Mods/Core/Defs/WorkTypeDefs/WorkTypes.xml`、`WorkGiverDefs/WorkGivers.xml`、`JobDefs/Jobs_Work.xml`、`ThinkTreeDefs/Humanlike.xml`

RimWorld 把「小人决定干什么」拆成四层，每层是一个**纯数据表**：

```
WorkType   （UI 上的一列：「医疗」「烹饪」「搬运」）   naturalPriority  列与列的顺序
   └ WorkGiver（一个具体找活儿的扫描器）              priorityInType   列内的顺序
        └ Job （找到的活：一个原子动作）              driverClass      怎么执行
             └ Toil（Job 拆成的状态机：走过去→占位→干活→收尾）
```

调度顺序**不写在代码里，写在 XML 的优先级树上**（`SubTrees_Misc.xml`）：

```xml
<li Class="JobGiver_Work"><emergency>true</emergency></li>   <!-- 救火、急救：压在一切之上 -->
<li Class="ThinkNode_ConditionalStarving"><JobGiver_GetFood/></li>
<li Class="ThinkNode_PrioritySorter">                        <!-- 下面这些按紧迫度竞争 -->
  <li Class="JobGiver_GetFood"/>
  <li Class="JobGiver_GetRest"/>
  <li Class="JobGiver_Work"/>                                <!-- 普通殖民工作，优先级最低 -->
</li>
```

**三个可以立刻用上的点**：

1. **紧急项硬编码在需求之上**。`emergency=true` 的活（救火/急救）不看需求直接抢断；而「吃饭」「睡觉」只是**和普通工作一起排进 PrioritySorter 竞争**。我们现在的实现是「 hunger < 25 直接打断任务」——按 RimWorld 的模型，应该让需求**参与竞争而不是无条件抢断**，否则小人会在战斗中途跑去吃饭。

2. **`WorkTypeDef.naturalPriority` 是整数，不是枚举**。列顺序是可比较的数值，所以「插到两个已知列之间」不需要改代码。我们的 `Actions` 表可以照抄：每个动作一个整数优先级，新动作插进去不用动别处。

3. **性格/特质不碰逻辑，只吐修正值**（`TraitDefs/Traits_Singular.xml`）：

```xml
<TraitDef>
  <defName>TooSmart</defName>
  <degreeDatas><li>
    <label>too smart</label>
    <statOffsets><GlobalLearningFactor>0.75</GlobalLearningFactor>
                 <MentalBreakThreshold>0.12</MentalBreakThreshold></statOffsets>
  </li></degreeDatas>
</TraitDef>
```

特质只有三种输出通道：`statOffsets`（属性加成表）、`skillGains`（技能加成）、以及工作标签过滤（`disabledWorkTags` / `requiredWorkTags`）。**特质永远不写 if/else，只往中心化的修正表里写数**。

这一条我们的 `personality` 现在是散在 `pawn.gd` 里做乘法的（勤快/懒散改干活速度、莽撞改战斗……）。抄成表以后加第 7 种性格就不用改代码：

```gdscript
## 性格 → 修正值。性格不写逻辑，只吐系数，全在 _speed_mult() 这几个口子上收口。
const TRAIT_MODS := {
    "勤快": {"work": 1.25, "decay": 1.10},
    "懒散": {"work": 0.80, "decay": 0.90},
    "莽撞": {"combat": 1.30, "work": 0.95},
    "胆小": {"combat": 0.75, "decay": 1.05},
    "心细": {"work": 1.10, "quality": 1.20},
    "结实": {"hp": 1.20, "decay": 0.90},
}

static func mod_of(trait: String, key: String, fallback := 1.0) -> float:
    return float(TRAIT_MODS.get(trait, {}).get(key, fallback))
```

**工作量**：性格表两小时；需求改为竞争制要动 `pawn.gd` 的状态机，半天。

### 1.4 8 邻域合并模型（自动图块）

**来源**：两份 Terraria 源码 + tModLoader 的 `patches/`。

Terraria 自动图块的**数据模型**值得记，**具体数值表不在**（tModLoader 仓库里只有 diff，反编译源码在 `Terraria-Source-Code-master` 里但是 18px 网格的手写分支树，抄不动）。

模型本身很简单：

- 每个邻居格对当前格有三种关系：**同类型**（合并）/ **空**（`-1`，露边）/ **异类型**（`-2`，硬边不混）
- 8 个邻居的状态合成一张查找表 → 目标图集格 `(frameX, frameY)`
- 另有 2 bit 的 `variant` 随机值，选 3 个纹理变体之一，**避免大片同一种地形看出重复**
- 任何一格变了，只重算它周围的 **3×3**（`SquareTileFrame`）

> 老实说：**本项目用不上完整版**。地面是色块烘焙，不接素材（见 `04-游戏内容.md` 美术一节），自动图块没有落点。这里记下来是因为第 2 节打包的 CC0 图块包自带一套 Godot 4 terrain set，将来如果地面改接素材，模型和资源是齐的。
>
> 真要接，别抄 Terraria 的递归 `mergeUp/mergeDown` 全局标记那套——那是为了跨材质混边（草接土）。**4 位基数掩码 + 一张 `Dictionary` 查找表**就能拿到 90% 的观感。

### 2.2 压缩：只省了 28%，为什么

原始 11.36 MB → 8.22 MB。**别期待更多，原因是这些素材本来就已经压得很紧了。**

做法是「raw 原文件 vs 几种重压候选，谁小用谁，压不小就原样拷贝」，绝不劣化。实测两类：

| 类型 | 例 | 原始 | 压缩后 | 手段 |
|---|---|---|---|---|
| 立绘 | `Actor3.png` | 169 KB | 29 KB（**-82%**） | 40,244 色 → 128 色量化 |
| 备用图块集 | `Outside_C.png` | 521 KB | 72 KB（**-86%**） | 85,500 色 → 128 色量化 |
| 气泡/图标 | `Balloon.png` | 26 KB | 8 KB（-69%） | 同上 |
| 已在用的行走图 | `Actor3.png` | 22 KB | 22 KB（**0%**） | 本来就是 109 色的调色板图，**转 RGBA 反而涨到 61 KB**，所以保持原样 |
| 音效 | `*.ogg` | — | 不变 | 环境里没有 ffmpeg，重编码做不了，原样搬 |

**结论**：省下的全是 RTP 里那批「像素画却存成 RGBA 真彩」的图（立绘、图块集）。**已经调色板化的行走图压不动，硬压会变大** —— 脚本里的 `image.mode == "P"` 分支就是防这个的。

**真正的「压缩」是不搬**：源目录 185.7 MB，其中 BGM 独占 76.9 MB、战斗背景 29 MB、动画 44.8 MB、视差图 3.5 MB —— 这些本项目一个都用不上。**搬之前先按用途筛，比搬完再压有效 20 倍。**

### 2.4 两个必须知道的缺口和风险

**缺口 1：七海和鱼和糖没有立绘。**
RTP 的 `Faces/` 只出了 12 张（Actor1~5、People1~4、Monster1、Evil、Spiritual），而七海用的是 `People6`、鱼和糖用的是 `People8` —— **这两个行走图在 RTP 里没有配套立绘**。现在这两人没有对口头像。

三个选项，选一个：
- （省事）给这两人换行走图到 `People1` / `People3`，立绘就齐了 —— 代价是 `Sprites.PAWN_SPRITES` 和 `selftest` 的断言要同步改
- （好看）从已有的 96 张头像里挑两张气质接近的凑上 —— 代价是立绘和行走图不是同一个人
- （不动）HUD 小人面板只显示名字 + 数值条，不放头像

**风险 2：RTP 素材的授权。**
RPGMaker VX Ace 的 RTP 素材（`Characters/` `Faces/` `Tilesets/` `Audio/` 全套）由 Gotcha Gotcha Games 授权，**标准条款限定用在「RPG Maker 制作的作品」里**。本项目是 Godot 工程，严格讲在这条线之外。

这不是我能替用户决定的事，但必须摆在明处：如果这个 Demo 只在自己机器上跑、不发布，无所谓；**一旦要公开发布，这批素材需要换成有明确许可的替代品**。对比之下，同一节里打包的 `assets/autotiles/`（CC0，作者 dandelion dino）就没有这个问题 —— 这也是为什么它值得留。
